## Bulgular (önem sırasıyla)

### PF-01 — critical / freeze-hang
- Dosya: `lib/services/automation_state.dart:1783`
- Belirti: LAN (direct) mode with a missing or invalid X-Device-Key (401), an unprovisioned board (403 unprovisioned) or a locked board (423): the dashboard shows an endless CircularProgressIndicator (dashboard_page.dart:1979-1986) while the app keeps requesting /api/status every 1.5 s forever. CONTRACTS section 3 locks a board for 60 s after 5 wrong keys (the lock scope, per client or global, is not defined there and the firmware portal has no lockout yet), so a stale phone can lock the board for everyone; the board serves HTTP with Arduino WebServer (WebPortal.h: WebServer _server, handleClient), one request at a time.
- Neden: _directRefreshImpl 401/403 branch (1783-1790) sets _directFailures = 0, retries _resolveLocalKey(forceRefresh: true) exactly once (_localKeyRefreshTried) and then simply continues; _connState is never moved off connecting, so status stays null. 423 (LocalApiException.isLocked / retryAfter) is not handled and falls into the generic failure branch (1791-1796). _startPolling (1742-1751) is a fixed clock.periodic: no backoff, no stop, no pause.
- Düzeltme: Replace the periodic timer by a one-shot timer re-armed after each completed request (cannot overlap): delay = interval on success, doubling up to 15 s with +/-20% jitter on network errors, reset on success. On 401/unprovisioned after the single key refresh: cancel the timer, set _connState = offline, keep _directError and expose a needs-key flag so the UI shows a card (re-fetch key / enter key / retry) instead of a spinner. On 423: pause for e.retryAfter (default 60 s). Resume on user retry, setLocalKey, selectDevice, setHost and app resume.
- Risk: Low. Direct mode only; keep the single-flight guard; tests built on StateHarness(directPollInterval:) and MockApi stay valid.
- Doğrulama: StateHarness + h.directMock.on('GET','/api/status',(r)=>jsonResponse({'error':'unauthorized'},status:401)); await h.clock.elapse(60s); expect h.directMock.count('GET','/api/status') <= 3, connState == offline, directError != null. Same with 423 and retry_after 60: one request in the first 60 s, resumes afterwards. Widget test: DashboardPage shows the error card and no CircularProgressIndicator.

### PF-02 — critical / freeze-hang
- Dosya: `lib/services/secure_storage_service.dart:87`
- Belirti: If any platform-channel call (Keystore/Keychain via flutter_secure_storage, local_auth probes) never answers, the app hangs with no recovery: the splash stays forever (AuthStatus.checking), or after the 15-minute access-token expiry every authenticated REST call that receives a 401 waits forever. Likelihood is platform dependent and not measured; the consequence is unrecoverable until restart.
- Neden: _read/_write/_delete (87-109) await the store with no timeout (try/catch only catches thrown errors). _initInner awaits four secure reads plus isBiometricEnabled sequentially (automation_state.dart:502-517) and biometric probes (biometric_auth_service.dart:15-25, 63-76) unguarded; the try/catch in _init (459-470) cannot catch a hang. _enqueueStorage (639-654) is a serial queue, so one stuck operation blocks every later write (logout wipe, token save). EvCloudApiService._doRefresh awaits onTokenRefreshed (ev_cloud_api_service.dart:362) which is _onTokenRefreshed -> _enqueueStorage (automation_state.dart:662-670): a stuck write blocks _refreshInFlight and with it every request waiting for the retry.
- Düzeltme: (1) In SecureStorageService wrap the three helpers: await _store.read(key).timeout(5 s) mapped to SecureStorageException(op, TimeoutException). (2) timeout(5 s) on isBiometricSupported/getBiometricLabel/getAvailableBiometrics (never on the interactive authenticate). (3) A per-operation timeout (about 8 s) inside _enqueueStorage so a stuck operation frees the queue. (4) In _doRefresh do not block the retried request on persistence: await callback(...).timeout(3 s, onTimeout) since the tokens are already in memory. (5) _init: wrap the non-interactive prefix of _initInner in .timeout(12 s) and fall back to unauthenticated plus storageError unless _awaitingUnlock.
- Risk: Low-medium: a timeout that is too short on a slow but working Keystore (first read after boot) would surface storageError; use 5-8 s and treat it like a read failure (the biometric flag is already fail-closed). Do not add methods to SecureKeyValueStore (InMemorySecureStore implements it).
- Doğrulama: Add a Completer-backed hangReads to InMemorySecureStore in test/support/fakes.dart; in testWidgets (FakeAsync) build StateHarness(autoInit: true) and pump 15 s: authStatus != checking and storageError != null. Second test: store.write hangs while MockApi answers 401 then 200: the retried request completes within the budget.
